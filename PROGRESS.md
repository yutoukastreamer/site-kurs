## 2026-06-09 — Интеграция отслеживания форм с Calltouch

**Задача:** передавать заявки с сайта kurs-gsi.ru в Calltouch (форма обратной
связи + кнопки «Получить предложение»).

**Что сделано:**
- Создан файл `public/calltouch-forms.js` — вся логика отслеживания.
- В `index.html` перед `</body>` подключён скрипт:
  `<script defer src="/calltouch-forms.js"></script>`.

**Как работает:**
- Слушатели висят на `document` (делегирование) — переживают перерисовку React
  и переходы между страницами SPA.
- **Форма обратной связи** (встроенная форма Bitrix24): перехватывается событие
  `submit`, поля имя/телефон/email читаются по эвристике (`type`/`name`/
  `placeholder`), телефон нормализуется к виду `79000000000`.
- **Кнопки «Получить предложение»** (это якорные ссылки на `#contact`, не сабмит):
  при клике запоминается продукт по URL (`/bulldozer`, `/excavator`, `/grader`),
  и его название подставляется в `subject`/`comment` при отправке формы.
- `sessionId` берётся через `window.ct('calltracking_params','4xv0727u')`.
- UTM-метки (`utm_source/medium/campaign/content/term`) собираются из URL.
- Отправка — чистый `fetch` POST на REST API Calltouch
  `https://api.calltouch.ru/calls-service/RestAPI/requests/82582/register/`.
- Логирование каждого шага в консоль (префикс `[Calltouch]`) + обработка ошибок.

**ID (подставлены в файл):** site_id `82582`, mod_id `4xv0727u`.

**Проверено в браузере (сквозной тест с перехватом fetch):**

### Диагностика на боевом домене + фикс мусорных заявок (9 июня 2026)

**Проверено вживую на kurs-gsi.ru через DevTools — интеграция РАБОТАЕТ:**
- [x] Скрипт `calltouch-forms.js` загружен и инициализирован.
- [x] Форма Bitrix24 рендерится в обычном DOM (НЕ iframe, НЕ Shadow DOM) —
      поля `name/email/phone` читаются; событие `submit` всплывает до `document`.
- [x] `sessionId` непустой: `3828188` (домен совпал, `siteId 82582`).
- [x] Реальный POST на `…/requests/82582/register/` вернул **200** и
      зарегистрировал заявку. CORS не мешает: запрос «простой»
      (`application/x-www-form-urlencoded`, без кастомных заголовков) — браузер
      preflight (OPTIONS) не шлёт. (OPTIONS у Calltouch не разрешён, но он и не
      нужен — это сбивало с толку при диагностике.)

**Найденный баг (причина «не работает» = мусор в журнале):**
- Поле телефона Bitrix24 предзаполнено маской `+7`. `normalizePhone('+7')` →
  `'7'` (непустая строка) → старая проверка «нет телефона и email» не срабатывала,
  и на КАЖДЫЙ сабмит (в т.ч. при проваленной валидации) уходила мусорная заявка
  с телефоном `7`. Calltouch их отсекает антифродом / журнал засоряется.

**Фикс в `public/calltouch-forms.js`:**
- Добавлены `isValidPhone` (≥11 цифр) и `isValidEmail` (`@` + точка).
- Отправляем только при валидном телефоне ИЛИ валидном email.
- Невалидные «огрызки» обнуляются перед отправкой (телефон-маска не попадёт в лид).
- Логика проверена на 5 кейсах (маска/неполный → SKIP; валидные → SEND).

**Что нужно сделать на стороне заказчика:**
- Пересобрать и **передеплоить** сайт (`npm run build` → `dist/`), чтобы прод
  отдавал исправленный `calltouch-forms.js`.
- В ЛК Calltouch удалить тестовую заявку «ТЕСТ интеграции форм» (создана при
  диагностике 09.06.2026, телефон 79000000000).

- Добавлена кнопка «На главную» (бордюрная, в стиле шапки).
- Анимация появления (framer-motion stagger) сохранена.

**Статус 404 vs 200 — это конфиг СЕРВЕРА, не код React.**
Проверено: боевой `kurs-gsi.ru` отдаёт `index.html` со статусом **200** на
любой несуществующий путь (server: nginx). То есть боевой сервер делает
SPA-fallback с кодом 200 и НЕ использует наш `nginx/nginx.conf`.

Приведены к единому поведению (известные маршруты → 200, остальное → 404):
- `public/.htaccess` — теперь возвращает настоящий 404 (`R=404` + `ErrorDocument`).
- `public/_redirects` — перечислены маршруты + `/* /404.html 404`.
- `nginx/nginx.conf` — уже отдавал 404 правильно.

## 2026-06-18 — Calltouch: устранены дубли заявок

**Проблема (от Calltouch):** заявки уходили «по каждому клику, даже если форма
невалидна» → дублирование.

**Причина:** `public/calltouch-forms.js` слушал родное DOM-событие `submit` и сам
угадывал валидность (длина телефона, regex email). Эта эвристика ≠ валидация
Битрикса, поэтому при невалидной форме Б24 заявка всё равно могла уйти в Calltouch.

**Фикс:** перешли на официальное событие Bitrix24 `b24:form:submit` и шлём заявку
только при `form.validated === true`. Поля читаем из `form.getFields()`
(`LEAD_*`/`CONTACT_*`). Вся прочая логика (sessionId, utm, «Получить предложение»,
отправка в REST API) сохранена. Удалён старый `submit`-перехватчик и самодельная
валидация — именно они давали дубли.
